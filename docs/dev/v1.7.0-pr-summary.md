# v1.7.0 PR Summary
## BL090: do/optimize dataset support + --apply speculative mapping

- Added a `--dataset-uri <s3://...>` flag to `do/optimize`. When supplied with `--goal throughput`, it passes a `DatasetConfig` (`InputDataConfig[].DataSource.S3DataSource.S3Uri`) to `CreateAIWorkloadConfig` and drops the `--no-optimize-model` workaround so a speculator can be trained. Without a dataset, throughput optimization preserves the existing `--no-optimize-model` behavior. The flag is validated as throughput-only and `s3://`-only. Documented the supported JSONL formats (ShareGPT, OpenAI Chat Completions, OpenAI Completions) in `--help` and `docs/optimize.md`.
- Extended `do/optimize --apply <arn|top>` to detect Speculative Decoding Configuration in `Recommendations[i].OptimizationDetails` and map it to the canonical `do/config` variables: `SpeculativeDecodingConfig.DraftModelArn` → `HP_SPECULATIVE_MODEL` (HF model ID when derivable, otherwise the full ARN), `NumSpeculativeTokens` → `HP_SPECULATIVE_NUM_TOKENS`, and an inferred `HP_SPECULATIVE_ALGORITHM` (`eagle3`/`eagle`/`draft-model`, defaulting to `draft-model`). `--apply` continues to write `OPTIMIZE_MODEL_PACKAGE_ARN`, `OPTIMIZE_INFERENCE_SPEC`, and `INSTANCE_TYPE`, so the next `do/deploy` applies the optimized package and speculative configuration in one run.
- Switched the HyperPod deploy guard to fire on a non-empty `HP_SPECULATIVE_ALGORITHM` (removing the non-existent `HP_SPECULATIVE_ENABLED`), and default `SGLANG_SPECULATIVE_NUM_STEPS` to the canonical `HP_SPECULATIVE_NUM_TOKENS` when no explicit step count is set.
- Added `test/unit/test_optimize_speculative_apply.py` covering the dataset-config wiring and executable `--apply` speculative mapping (EAGLE3, ARN-embedded HF ID extraction, and the empty-details skip path), and updated the BL085 contract test for the new guard. `uv run pytest test/unit/` (870 passed, 1 skipped) and the speculative-decoding JS suite pass.

## BL088: HyperPod EKS InferenceEndpointConfig CRD migration

- Migrated the HyperPod EKS deployment target from raw Kubernetes `Deployment`, `Service`, and `ConfigMap` manifests to a single `InferenceEndpointConfig` custom resource (`templates/hyperpod/InferenceEndpointConfig.yaml.ejs`), reconciled by the `amazon-sagemaker-hyperpod-inference` operator. Removed the legacy `deployment.yaml`, `service.yaml`, `configmap.yaml`, and `pvc.yaml` templates — the operator now provisions the serving workload and model storage.
- Verified the CRD schema against `kubectl explain inferenceendpointconfig --recursive` and the AWS docs before implementation: `spec.worker.environmentVariables` (not `spec.worker.env`), `spec.modelSourceConfig.s3Storage.{bucketName,region}` (parsed from `STAGED_MODEL_PATH`, not a full `s3://` URI), and required `spec.modelName`. Confirmed `spec.worker.args` and `spec.worker.environmentVariables` both exist, unblocking BL085's speculative-flag injection.
- Rewrote `do/deploy.d/hyperpod-eks` to render the model source conditionally (S3 when staged, otherwise Hugging Face with a `hf-token-secret` `tokenSecretRef`), apply the CRD, poll `status.state` until `DeploymentComplete`, then poll `aws sagemaker describe-endpoint` until `InService` (15-minute cap). On success it writes `ENDPOINT_NAME=$PROJECT_NAME` and sets `DEPLOYMENT_TARGET_HP_STATUS=Running` only after `InService`; failure/timeout records `Failed`.
- Updated `do/clean.d/hyperpod-eks` to delete the `InferenceEndpointConfig`, wait for the `SageMakerEndpointRegistration` to be removed, and clear `ENDPOINT_NAME`.
- Preserved workflow compatibility: `do/test --target hyperpod-eks` resolves and port-forwards the operator-created Service (defaulting to the project name), `do/logs --target hyperpod-eks` falls back across operator pod-label conventions, and `do/benchmark` targets the registered endpoint directly (no inference component).
- Added `.ejs` suffix stripping to the template copier so `*.yaml.ejs` renders to `*.yaml` in generated projects and via `mcc regenerate`.
- Updated and added regression coverage: migrated the raw-manifest property/unit tests to the CRD contract, added `hyperpod-crd-deploy-driver.test.js` for the deploy/clean driver contract and S3/HF model-source rendering, and re-homed the manifest-side speculative tests to BL085 while keeping the serve-script guards. Full JS suite and `uv run pytest test/unit/` pass (pre-existing, environment-only `notebook-export` and cluster-picker subprocess timeouts excluded).

## BL085: HyperPod speculative-decoding CRD migration

- Migrated speculative decoding to the `InferenceEndpointConfig` worker environment contract without using `spec.worker.args`. The CRD emits both vLLM and SGLang engine-specific variables; the selected image wrapper translates only its applicable set into server flags.
- Enabled the documented `HP_SPECULATIVE_*` configuration exports in both HyperPod `do/config` branches. User-facing algorithms map to vLLM's underscored methods and SGLang's uppercase enum values, including `draft-model` → `draft_model` / `STANDALONE` and `eagle2` → `eagle2` / `EAGLE`.
- Updated the wrappers to build vLLM `--speculative-config` JSON and SGLang discrete `--speculative-*` flags from their engine-specific variables. Both reject `s3://` draft-model URIs at startup.
- Added CRD rendering and wrapper contract coverage for every supported algorithm, the disabled path, S3 validation, and the no-`worker.args` requirement.
